02 / Tech Stack

기술 스택

기술 이름마다 실제로 쓴 곳, 내가 한 일, 그 기술을 쓴 이유를 함께 적었습니다.

C# · .NET MAUI Blazor Hybrid

App

어디에
잼박스 Android · Windows 앱 전체
한 일
화면·라우팅·로그인 상태 관리, GPS(Geolocation)·카메라(MediaPicker)·보안 저장소(SecureStorage)·공유 시트 연동, 안드로이드 뒤로가기 처리
이유
웹(Blazor)과 같은 C#·Razor 화면과 API 클라이언트를 함께 쓰기 위한 팀의 선택 — 웹 기능을 빠르게 앱으로 옮길 수 있었다

HTML · CSS · JavaScript

UI

어디에
앱 화면 스타일, 네이버 지도 JS 연동, 이 사이트
한 일
지도 마커·위치 찍기 스크립트를 .NET과 JS interop으로 연결, 아래 목록 시트를 손가락으로 끌어 올리는 터치 처리(sheet.js)
이유
지도처럼 C#만으로 그릴 수 없는 부분은 웹 표준 기술로 처리하는 것이 가장 단순했다

ASP.NET Core Minimal API

Server

어디에
잼박스 API (서버는 팀장 담당, 앱은 이 API를 호출)
한 일
앱 버전 확인 엔드포인트 GET /api/app-version 추가, 로그인 토큰으로 본인을 확인하는 API로 바뀌었을 때 앱의 모든 호출 부분 수정
이유
업데이트 기준 버전을 앱이 아니라 서버 설정에서 바꿀 수 있어야 했다

PostgreSQL · Supabase

Data · Auth

어디에
로그인(Supabase Auth), 일지·투표·도장 테이블
한 일
구글·카카오 OAuth 로그인을 앱에 연결, SNS 첫 가입자의 정보 입력 대기 흐름 구현, 서비스 장애 때 DNS 조회로 원인(프로젝트 일시 정지) 확인
이유
이메일·SNS 로그인을 직접 만들지 않고 검증된 인증 서비스를 쓰기 위해(팀 결정)

AWS (EC2 · RDS · S3 · IAM 역할)

Infra

어디에
잼박스 배포 서버(팀장이 EC2에 배포), 학교 AWS 계정
한 일
접근 키 발급이 막힌 학교 계정 조건에서 EC2 인스턴스 프로필로 S3를 쓰도록 순서를 설계해 팀 문서(docs/09-2)로 정리
이유
키를 설정 파일에 두지 않고 역할로 권한을 주는 편이 안전하고, 학교 정책에도 맞았다

Android 빌드 · Git

Deploy · Collab

어디에
Release APK · AAB, 멤버별 브랜치
한 일
서명된 Release APK·AAB를 만들어 배포 폴더 교체, 버전 규칙(0.9.2 → versionCode 902) 정리, 팀장 브랜치를 병합할 때마다 앱 빌드 확인
이유
공용 코드가 바뀌면 앱이 먼저 깨지기 때문에, 병합 직후 검증하는 습관이 필요했다

03 / About

소개

컴퓨터공학과 3학년입니다. 수업에서 배운 화면·데이터·클라우드를 팀 프로젝트 하나로 이어 보며, 사용자가 실제로 쓰는 앱을 만드는 데 관심이 생겼습니다.

협업 방식

  • 웹(팀장)과 앱(나)을 나눠 맡고, 멤버별 브랜치에서 작업 후 PR로 합쳤습니다.
  • 여러 사람이 쓰는 공용 코드(API·공유 모델)를 바꿀 때는 먼저 알렸습니다.
  • 팀원 수정 요청을 받으면 목록으로 정리해 하나씩 처리하고 결과를 공유했습니다.

활동

  • 2026 신구 엑스포 — 잼박스 프로젝트 전시·시연
  • 주간 보고서 작성, 발표·시연 대본 준비
  • 팀 문서 작성 — 학교 AWS 계정 설정 순서(docs/09-2)

배운 점

직접 써 보며 불편한 점을 찾고 고치는 일이 UI/UX 수업에서 배운 내용과 같다는 것을 느꼈습니다.

오류가 나면 추측보다 네트워크 → 외부 서비스 → 코드 순서로 원인을 좁히는 습관을 들였습니다.

다음에 하고 싶은 것

  • 실제 사용자 의견을 받아 앱 경험 개선하기
